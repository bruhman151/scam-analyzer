# แผนทำ Scam Risk Analyzer MVP ภายใน 7 วัน

**เป้าหมาย:** โปรแกรมประเมินความเสี่ยงทำงานในเครื่องเป็น HTTP service; ผู้ให้บริการจำลองส่งข้อความ/URL/ภาพเข้าไปและรับสถานะการวิเคราะห์ ระดับความเสี่ยงเมื่อมีหลักฐาน เหตุผล และคำแนะนำกลับมา

| วัน | งาน | Gate ที่ต้องตรวจด้วยตนเอง | หลักฐานสำหรับ portfolio |
|---|---|---|---|
| 1 | ศึกษารูปแบบโจมตีจากแหล่งที่มา, กำหนด API contract และตัวอย่างทดสอบ, ทำข้อความหนึ่งกรณีให้รันได้, ตรวจความพร้อม OCR | เจ้าของโปรเจกต์อธิบาย input/output และข้อจำกัดของกฎแรกได้ | ตารางแหล่งข้อมูล, design decision, ผล smoke test |
| 2 | ขยายกฎข้อความไทย/อังกฤษและคะแนน | เคส scam ชัดเจนกับข้อความปกติไม่ถูกเหมารวม | ผล unit tests, false positive แรก |
| 3 | ทำ provider simulator และทดสอบ HTTP end-to-end | ส่งข้อความจำลองเข้า service และเห็น JSON ผลลัพธ์ | ภาพ demo และ integration test |
| 4 | วิเคราะห์ URL แบบไม่เปิดลิงก์ | URL ปกติไม่ถูกจัด HIGH จากการมีลิงก์อย่างเดียว | ก่อน/หลังการแก้กฎ URL |
| 5 | รับภาพและ OCR ไทย/อังกฤษ | ภาพอ่านได้เข้าตัววิเคราะห์; ภาพอ่านไม่ได้แสดงสถานะไม่สมบูรณ์ | ภาพ OCR input/output และ failure case |
| 6 | ทดสอบเคสใหม่ที่ไม่ได้ใช้คิดกฎ, แก้จุดพลาด, README และซ้อม demo | ชุดทดสอบผ่าน; อธิบาย architecture/limitations ได้ | test report, architecture diagram, demo |
| 7 | เวลาสำรองสำหรับปัญหา OCR, ทดสอบซ้ำ และเก็บหลักฐาน | demo รันจากคำสั่งใน README ได้ | milestone Git และ screenshot สุดท้าย |

หลักการทุกวัน: **BUILD → RUN → TEST → BREAK → FIX → DOCUMENT** เมื่อแก้กฎให้บันทึกตัวอย่างที่ทำให้พลาดและผลหลังแก้ ห้ามอ้าง accuracy หรือประสิทธิภาพโดยไม่มีการวัดจริง

## สถานะเมื่อ 5 ตุลาคม 2026

งานในแผน MVP ครบทั้ง API จำลองผู้ให้บริการ, วิเคราะห์ข้อความ/URL/ภาพ, OCR ไทย/อังกฤษ, ทดสอบกรณีปกติและกรณีผิดพลาด, ประเมินตัวอย่างใหม่, วัดผล optimization และเอกสาร portfolio แล้ว หลักฐานปัจจุบันอยู่ใน `docs/integration-results.json`, `docs/evaluation-results.json`, `docs/benchmark-results.json` และ `docs/PORTFOLIO.md` งานต่อยอดจริงยังต้องมีข้อมูลที่ได้รับความยินยอมและชุดทดสอบอิสระ

## การทดสอบ

1. **ชุดสร้างกฎ:** ตัวอย่างใน `tests/cases.json` ระบุ *ผลที่คาดหวัง* ไม่ใช่ผลจริง
2. **ชุดทดสอบใหม่:** วันที่ 6 เพิ่มตัวอย่างที่ไม่เคยใช้เลือกคำและน้ำหนักกฎ เพื่อดู false positive/false negative
3. **API tests:** ข้อความว่าง, ชนิดข้อมูลผิด, ไฟล์ใหญ่/อ่านไม่ได้ และผลตอบกลับที่มี field ครบ
4. **End-to-end:** เปิด service แล้วส่งเหตุการณ์จาก provider simulator จริง

ใช้ข้อความสังเคราะห์หรือข้อความที่ลบข้อมูลส่วนบุคคลแล้ว ไม่เก็บ input ที่ผู้ใช้ส่งมาเป็น log หรือฐานข้อมูลใน MVP

## จุดเสี่ยงที่ต้องตัดสินใจเร็ว

- OCR Thai/English: เครื่องที่ตรวจในวัน 1 ยังไม่พบ Tesseract; ต้องทำ installation และ smoke test ก่อนถือว่าฟีเจอร์ภาพเป็นไปได้
- การใช้ URL: ตรวจโครงสร้างและบริบทเท่านั้น ไม่ fetch URL ไม่ตรวจชื่อเสียงโดเมนสด
- คะแนน: น้ำหนักเริ่มต้นเป็น heuristic ต้องปรับจากตัวอย่างทดสอบจริง ไม่ตีความเป็นเปอร์เซ็นต์
